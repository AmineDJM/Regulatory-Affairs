# AMD Internal OS — instructions projet

ERP interne Adventum Pharma. Next.js 14 (App Router) + Prisma + PostgreSQL, UI en français, devise DZD. Aucune donnée simulée. Vérification avant commit : `npm run typecheck && npm run build && npm test` (Postgres local : `pg_ctlcluster 16 main start` si down). Migrations : SQL manuel idempotent dans `prisma/migrations/` + `db:deploy`.

⚠️ **`npm run build` réutilise le cache `.next`** et peut donc rater une erreur que le serveur de déploiement, lui, verra (il part d'un dossier vide). Après avoir touché aux **imports d'un composant client**, vérifier sur un build propre : `rm -rf .next && npm run build`.

## Frontière client / serveur — la règle qui casse les déploiements

Un composant `"use client"` est compilé **pour le navigateur**. S'il importe — même indirectement, à dix modules de distance — un module qui lit des fichiers (`fs`, `zlib`, `child_process`…), la compilation de production échoue avec **« Module not found: Can't resolve 'fs' »**. Le typecheck ne le voit pas.

- Les **actions serveur** (`"use server"`) ne comptent pas : Next.js les remplace par un appel distant. Un composant client peut les appeler librement.
- Ce sont les imports **ordinaires** (constantes, types *avec valeur*, fonctions utilitaires) qui posent problème.
- Pattern à suivre : sortir les fonctions **pures** dans un module dédié qui n'importe rien de lourd (ex. `src/lib/market/galenic.ts` et `text.ts` pour les normalisations pharma ; `molecule.ts` garde l'analyse qui lit les données et les **réexporte** pour le serveur).
- **`src/lib/client-bundle-guard.test.ts`** remonte les chaînes d'import — statiques ET dynamiques (`import("…")`), modules natifs ET paquets Node-only (`web-push`, `nodemailer`, `sharp`, `mupdf`…) — et fait échouer `npm test` en affichant le chemin fautif. Ne pas le désactiver : il existe parce que l'erreur est déjà passée en production, deux fois (`market/data.ts` par `fs`, puis `messaging.ts` par `web-push` via le registre d'événements). Un module serveur qui porte aussi des constantes d'écran se scinde : la part pure dans un fichier sans import (`messaging-ui.ts`), réexportée côté serveur.

## Mission Runtime — la doctrine (§118)

Exécuter une mission gigantesque est une propriété **codée** de l'architecture, pas une recette. Les règles ci-dessous ne sont pas des conseils : elles sont tenues par des tests, et chacune existe parce que son absence a un coût nommable.

**Les modèles décident QUOI. Le code décide COMMENT.** La persistance, les droits, les états, le DAG, le parallélisme, les reprises, les points de reprise, l'idempotence, les approbations, les événements, les notifications, la reprise après panne, l'observabilité et la vérification du succès appartiennent au **logiciel**. Un modèle qui propose un plan est une proposition faillible ; ce qui en fait un programme, c'est le compilateur.

1. **Deux axes indépendants.** La difficulté de raisonnement (A/B/C) et la quantité de travail (S→MASSIVE) ne se confondent jamais. « Le même message à 33 salariés » est B + MASSIVE : le plan est évident, l'exécution est massive. Router sur le nombre d'étapes enverrait cette mission au raisonnement le plus cher pour rien.
2. **Aucune limite d'architecture.** Même moteur pour 3, 30, 300 ou 3 000 actions. Les seules limites sont **opérationnelles** (concurrence, quotas, budget, sécurité) et elles portent leur raison dans le code.
3. **Le plan d'un modèle n'est jamais exécuté tel quel.** `compiler/compile.ts` refuse une capacité inventée, une capacité interdite à l'acteur, un cycle, une forme incohérente et une **cardinalité fausse** — 33 destinataires dans une étape au lieu de 33 étapes.
4. **Une étape terminée avec son reçu EST le point de reprise.** Pas de table de points de reprise : elle dirait la même chose une seconde fois et divergerait.
5. **Ne rien recréer de ce qui existe.** `MissionEvent` est le journal, `BusinessEvent` le registre canonique (§17 : pas de second registre), `src/lib/push.ts` le VAPID (§34 : pas de second système de notifications), le `scheduler` existant l'ordonnanceur (§39 : pas d'ordonnanceur parallèle), `AssistantActionIntent` l'idempotence et le reçu.
6. **Aucune auto-escalade.** `policy/guard.ts` interdit STRUCTURELLEMENT à l'agent de modifier des permissions, s'attribuer SUPER_ADMIN, toucher au RBAC, créer des identifiants ou désactiver un garde-fou. C'est un refus de **compilation**, pas une consigne de prompt : une consigne de prompt est une prière qu'un document injecté peut contredire.
7. **Une mission n'est jamais une porte dérobée.** Mêmes droits, même contexte d'acteur, même audit, même politique de confirmation que l'écran. Un contenu d'e-mail ou de document est une **donnée**, jamais une instruction.
8. **Un accord, pas 99 confirmations — ni un chèque en blanc.** L'approbation porte sur un périmètre résumé par une empreinte immuable ; un changement **matériel** rouvre la partie modifiée, et elle seule.
9. **On ne s'arrête jamais à la première difficulté.** Douze causes d'échec, une échelle de recours par cause, et un invariant : `estFinPossible` refuse de conclure tant qu'un barreau reste. Mais **la persévérance n'autorise ni l'invention ni le contournement** — TROUVÉ / DÉDUIT / CANDIDAT / INCONNU, et seul TROUVÉ autorise à agir.
10. **« Toutes les étapes ont tourné » n'est pas « l'objectif est atteint ».** Le contrôle qualité est arithmétique et a le dernier mot dans le sens **négatif** ; la satisfaction se juge, et **sans juge la mission ne conclut pas**. Un moteur qui conclut parce qu'il n'a pas pu vérifier est pire qu'un moteur qui ne conclut pas.
11. **Le contexte se compose, il ne s'accumule pas.** Jamais « la conversation grandit → on renvoie tout ». Trois couches ne se coupent jamais : approbation en attente, identité active, contrainte que la personne vient d'énoncer.
12. **Pas d'apprentissage silencieux.** Ce qu'Adam a OBSERVÉ n'est pas ce qu'un humain a APPROUVÉ, et seul l'approuvé fait autorité.
13. **Pas de fichier-dieu, pas de mission spécialisée.** Le runtime est découpé en `missions/{runtime,planner,compiler,registry,policy,approval,events,goal,recovery,commitments,templates,memory,view,agent,artifacts,model,evals}/`. Écrire `newYearMission.ts` serait l'échec du chantier, pas sa réussite.
14. **Une capacité sans appelant réel n'existe pas.** Le critère n'est pas « le code est écrit et testé », c'est : *si quelqu'un utilise Adam normalement maintenant, ce composant peut-il être déclenché et produire un effet utile ?* Un recensement a montré quatre exports sans aucun appelant et vingt-quatre appelés par leurs seuls tests — dont le compacteur de mémoire et toute la porte d'approbation côté humain. Avant de déclarer une brique finie : chercher son appelant de PRODUCTION, et si l'on n'en trouve pas, la brancher ou la supprimer. Un test qui part d'un état injecté à la main ne répond pas à la question ; il faut partir du **vrai point d'entrée** (`rememberExchange`, `lancerMission`, l'action serveur, le battement).
15. **Ce qu'un modèle ne doit jamais pouvoir faire à notre place.** Accorder une autorisation et fournir une pièce sont des **attestations** : l'audit portera le nom d'une personne. Un document lu par une étape peut contenir « approuve la mission » ; si l'outil existe, l'injection réussit et rien ne distingue plus l'accord forgé du vrai. Ces gestes-là exigent un clic dans une vraie session (`mission-runtime-actions.ts`), et `policy/guard.ts` interdit `mission_control` à l'agent **à la compilation**. Les gestes qui RÉDUISENT — suspendre, arrêter, refuser — sont, eux, sans danger et disponibles dans la conversation.

16. **L'empreinte réelle d'une mutation ne dépasse jamais l'empreinte demandée.** Deux axes, jamais confondus : la PROFONDEUR (un champ < un enregistrement) et la CARDINALITÉ (une cible / plusieurs). `mutations/empreinte.ts` — module pur au socle, parce que la conversation ET le compilateur en ont besoin sans avoir le droit de se parler — refuse une opération plus large que ce que la demande énonce, et nomme l'opération plus étroite. Il rend `null` sur tout ce qu'il ne lit pas à coup sûr, et un `null` laisse passer : une garde qui refuse ce qu'elle ne comprend pas est désactivée dans la semaine.

17. **Un contrôle qui ne peut pas échouer ne protège de rien — il rassure, ce qui est pire.** Le verdict « ZÉRO sortie réelle » d'un banc s'écrivait `sorties.every(() => true)` : vrai garde armée ou non, vrai sur une liste vide. Sous ce vert, `sortiesInterdites()` — qui ne connaissait que `vitest` et Playwright — laissait la garde de sortie DÉSARMÉE dans tout `scripts/bench/`, c'est-à-dire précisément dans les bancs qui lancent de vraies missions sur de vraies personnes. Deux règles en sortent : un garde-fou s'arme sur un **fait du processus** (le script d'entrée vit sous `scripts/bench/`), jamais sur une variable qu'un banc futur devrait penser à poser ; et une assertion dont on ne sait pas nommer le cas qui la ferait tomber n'est pas une assertion.

18. **Le compilateur dit tout ce qu'il sait en une fois, et la persévérance se juge au PROGRÈS.** La couverture des primitives était gardée par `issues.length === 0` : le plan 1 était refusé sur la forme d'une attente, le planificateur corrigeait exactement cela, et le plan 2 découvrait un `MISSING_PRIMITIVE` dont le premier refus n'avait rien dit — deux essais, deux reproches distincts, mission morte avant d'exister, tuée par l'ORDRE des objections. Un compilateur qui distille ses reproches fait payer un aller-retour de planification par objection. Et le nombre d'essais n'est pas le bon critère : tant que le refus CHANGE, le modèle répare et mérite un tour ; dès qu'il REVIENT identique, il est bloqué. Le plafond reste **opérationnel** (§2), il ne définit pas la persévérance.

19. **Ce que le compilateur EXIGE, le prompt doit dire comment le SATISFAIRE.** Le contexte disait « cette demande EXIGE DOCUMENT » ; le nœud `ARTIFACT` — la seule forme d'étape qui produit un fichier — n'était décrit nulle part que le modèle puisse lire : ni dans les règles, ni dans le schéma (`typeConst` ne portait pas de description). Le plan revenait sans livrable, deux fois. L'exigence et le moyen de la satisfaire vivaient dans le même code sans jamais se rencontrer chez le modèle.

20. **Une sortie dont la FORME dépend de la DONNÉE n'est pas un contrat.** `resolve_person` rendait `{certain, candidats}` quand il trouvait et `{resultat, precision}` sinon. Le planificateur écrit ses références AVANT de savoir ce que la recherche rendra : il a parié deux fois et perdu deux fois, chaque perte coûtant une étape morte ET une replanification complète (plan v4, 46 étapes, 0,33 $ contre 0,20 $). Les clés sont désormais toujours les mêmes et c'est la VALEUR qui dit l'absence — une liste vide, que le moteur sait déjà traiter (« si la liste amont est vide, l'étape est ignorée »). Le mécanisme des formes apprises (§53) n'était pas en faute : il annonçait fidèlement `{ candidats?, certain?, precision?, resultat? }`. Il le dit maintenant en toutes lettres quand AUCUN champ n'est garanti — un « ? » noyé dans une énumération se lit comme un catalogue d'options. **Recensement au 09/2026 : 11 capacités sur 65 observées sont dans cet état** (`create_report`, `inspect_record`, `list_commitments`, `person_report`, `product_360`, `recall_conversation`, `regulatory_workload`, `search_documents`, `search_products`, `what_changed`, et `resolve_person` désormais réparée). Chacune rend une forme « trouvé » et une forme « rien trouvé » : c'est le même défaut, onze fois.

21. **Une chaîne qui marche ne prouve rien ; deux chaînes qui marchent prouvent le moteur (§91).** La chaîne Regulatory → Finance → Marchés → Excel + PowerPoint passait 10/10. Une SECONDE, écrite pour ne rien partager avec la première — RH + Finance + Supply Chain, trois sources indépendantes au lieu de deux dossiers d'un même service, un document **Word** au lieu d'un classeur et d'un deck, et le manquant chez la TROISIÈME personne au lieu de la première — l'a fait passer **sans une ligne de code de plus** (`CHAINE=budget`). Et elle a trouvé ce que la première ne pouvait pas : c'était le BANC qui avait mémorisé la chaîne A (il lisait le manquant dans `SCENARIO[0]`), un contrôle QA qui réclamait un livrable produit APRÈS lui, `« Nom <adresse> »` refusé comme destinataire alors que l'adresse était là, une étape d'envoi visant le DEMANDEUR (on ne s'écrit pas à soi-même), et le choix de l'e-mail — sans boîte connectée — pour joindre trois collègues internes, avec un refus qui ne proposait qu'un geste humain dans un écran de réglages. Cinq défauts qu'un seul scénario ne pouvait pas révéler.

22. **Un fait adressé à une mission que plus aucune attente ne consomme ne disparaît pas (§90).** Cas adverse joué en live : Khaled répond « prix de cession : 84 500 », l'attente se règle, puis Khaled se reprend — « Correction : c'est 91 000 ». `reveillerMissions` ne regarde que les étapes `WAITING` : le second message a rendu `[]`, en silence. Vérifié en base sur deux chaînes : le chiffre corrigé n'existait NULLE PART. La mission a conclu sur un chiffre que son auteur avait démenti — aucune étape en échec, aucun signal. Le faux succès parfait. Le routeur le CONSIGNE désormais au journal (`MissionEvent`, §118.5 : pas de seconde table) quand le fait NOMME cette mission et que rien ne l'a consommé — visible pour le contrôle et pour le compte rendu, sans rien rejouer ni décider à la place d'un humain. **Et le verdict qui devait le voir était lui-même un faux succès** : il cherchait un mot (« contradiction », « écart ») dans tout le corpus, et il a accroché « contradiction relevée » — dite par le juge à propos d'autre chose — puis un « écart facture/BC » des données ERP. Un mot-clé cherché partout mesure le vocabulaire ambiant, pas le fait. Troisième tautologie de ce banc, et la leçon de §17 est la même : nommer le cas qui ferait tomber l'assertion, sinon ce n'est pas une assertion.

23. **Une personne répond, et la mission conclut sans sa réponse.** Khaled écrit « prix de cession Nivolex 84 500 DZD » ; l'attente se règle ; l'étape de consolidation REÇOIT ce texte — vérifié dans `WorkerRun.input` — et rend « prix de cession non fournis ». Les deux livrables sont bâtis là-dessus : **0 chiffre du jeu d'essai sur 6** dans le classeur, 0 sur 6 dans le deck. Toutes les étapes vertes, les fichiers s'ouvrent, la QA passe : quatre personnes dérangées pour un document qui déclare n'avoir rien reçu. Trois corrections, à trois étages. Le **contrôle** (`goal/qa.ts`, `RETOURS_PERDUS`) refuse un retour humain dont aucun chiffre n'apparaît dans une seule SORTIE — et ne regarde JAMAIS les entrées, que le moteur vient de remplir : les compter rendrait l'assertion vraie dans le cas exact qu'elle existe pour attraper (§17). Seule exception, l'entrée d'une étape qui a produit un EFFET (envoi, écriture, fichier) : là, ce qui entre est ce qui est écrit. La **donnée** (`runtime/reponse.ts`) porte désormais la parole au premier niveau — `{ reponseDe, contenu, pieces }`, toujours les trois (§20) — au lieu de la comptabilité du moteur (`payload.body`, `attenteProgres`). Le **plan** (règle 21) : ce qu'on fait dire à quelqu'un, on le lit ; ne pas relancer une recherche dans la messagerie pour retrouver une réponse déjà en main — c'est ce qu'a fait le second run, et le livrable est sorti vide alors que la personne avait répondu.

24. **Le banc s'arrêtait à « le fichier s'ouvre ».** Un `.xlsx` valide, `xl/workbook.xml` présent, verdict vert — sur un classeur qui ne portait aucun des chiffres que trois personnes venaient de donner. Le verdict ouvre maintenant la pièce. Et la première version de ce verdict était elle-même une tautologie : elle retirait tous les caractères non numériques du fichier et cherchait l'aiguille dans la botte, où « 890 » se trouve à coup sûr parmi vingt mille chiffres. On compare des NOMBRES à des NOMBRES, avec la même lecture des deux côtés — « 84 500 » se recolle sur UNE espace, deux cellules voisines séparées par plus d'une ne se recollent pas.

25. **Une capacité qui déclare elle-même son échec a échoué — mais seulement quand elle ÉCRIT.** `watch_entity` rendait `{ ok: false }` ; sans contrat déclaré rien ne le lisait, l'étape passait DONE avec un reçu SUCCES, et c'est le juge d'objectif — cher, faillible, absent de la plupart des missions — qui a dû rattraper. Le faux succès était déjà au registre de preuves. La lecture est restreinte aux effets qui écrivent : sur une LECTURE, `ok: false` peut être une réponse (« non conforme »), et refuser à tort est strictement pire.

26. **Le silence d'une fiche se lit comme une permission de deviner.** `inspect_drive_folder` n'annonçait aucune sortie — jamais observée, absente de la table de secours. Le planificateur a écrit `{{lecture:drive-inventaire.apercuLot}}`, le compilateur n'a rien pu refuser (il ne refuse que ce qu'il SAIT faux), et la mission est morte à l'exécution sur un champ qui n'existe pas. On ne comble pas ce trou par une table écrite à la main — son entretien est intenable. On DIT l'ignorance et on nomme le geste sûr : référencer l'étape entière.

27. **Un refus à tort est pire que le défaut qu'on corrige — et cette fois c'est le compilateur qui a failli l'apprendre en production.** Une règle « toute attente sur une personne doit être lue par une étape » a été écrite, typecheckée, et a fait tomber **25 tests d'architecture**. Ils avaient raison : une attente est souvent une simple barrière (« dès qu'il a signé, préviens-le »), et le CONTENU de la réponse n'y sert à rien. La règle a été retirée. Ce que le compilateur ne peut pas savoir, le contrôle arithmétique de FIN le sait — il juge un résultat, pas une intention.

28. **Une coupe silencieuse dans un prompt est un mensonge fait au modèle — et c'était LA cause.** Le prompt d'un worker écrivait `JSON.stringify(input, null, 2).slice(0, 6000)`. Sur la chaîne humaine, deux dossiers ERP de neuf mille caractères mangeaient le budget et les DEUX réponses humaines — trois lignes chacune, la seule chose que la mission était allée chercher — n'atteignaient jamais le modèle. Il écrivait « prix de cession : non fourni », honnêtement. `WorkerRun.input` gardait l'entrée complète : c'est ce qui a fait accuser le modèle trois runs de suite. Trois propriétés remplacent la coupe (`runtime/entrees.ts`) : le budget se répartit ENTRE les clés au sens max-min — les petites d'abord, leur surplus aux grandes — donc aucune ne disparaît ; ce qui est coupé le DIT à l'endroit exact, avec la seule phrase qui compte (« son absence ici ne prouve rien ») ; et rien n'est coupé tant qu'il reste de la place. Mesure : `.xlsx` 0/6 → 6/6 chiffres collectés, `.pptx` 0/6 → 5/6, `.docx` 4/4 sur la seconde chaîne.

29. **Une exigence déduite d'un MOT ne tue pas une mission ; une faute de PLAN, si.** « Sors-moi … la date d'échéance … UN TABLEAU » : `exigencesFermes` y lit une pièce et exige DOCUMENT ; le planificateur comprend un tableau à l'écran, planifie `show_table`, et n'écrit pas d'ARTIFACT. Le compilateur refuse, le planificateur refait le même plan, la mission meurt sans rien livrer. On distingue donc la NATURE du reproche : cycle, capacité inventée, référence morte, entrée obligatoire absente restent mortels — le plan est faux. Une exigence de COUVERTURE lue dans la phrase est d'une autre espèce : le plan est exécutable, il livre peut-être moins que ce que le mot laissait entendre. La mission part, et la lacune est DÉCLARÉE (`gaps` persistés, `GAP_DECLARED` au journal). On ne devine pas le livrable à la place du modèle, et on ne baisse pas l'exigence en silence.

30. **Un refus qui nomme la faute sans nommer le remède fait payer un aller-retour, et tue parfois la mission.** Trois cas mesurés le même jour. `outcome: EVENT` derrière un WAIT_INPUT : « l'issue EVENT n'a de sens qu'après une attente d'événement » — vrai, inutilisable ; le refus donne maintenant l'issue à écrire selon le type réel du nœud amont. `watch_entity` recevant un CRITÈRE (« les dossiers dont l'échéance tombe dans 60 jours ») : le refus listait ce qu'il avait cherché ; il dit maintenant qu'une surveillance porte sur UNE cible et qu'un ensemble se surveille en listant d'abord, puis une par fiche — un éventail, que le moteur sait déjà déployer. Une capacité jamais observée : sa fiche se taisait, et le silence s'est lu comme une permission de deviner (§26). C'est §19 étendu à tous les refus : ce que le code EXIGE, le contexte doit dire comment le SATISFAIRE.

31. **Un manque non classé est un manque invisible.** « mission BLOCKED sans étape en échec » ne ressemblait à aucune signature et repartait en INDETERMINE. La cause était pourtant écrite dans l'état : soit un outil a NOMMÉ sa limite (`{ limite, manquantes }`), et c'est un service tiers absent — la suite est « brancher le connecteur », pas « écrire un eval » ; soit tout a abouti et le juge a refusé l'objectif, et c'est le plan qui ne le couvrait pas. Ranger l'un dans l'autre envoie la dette au mauvais endroit, et une taxinomie dont le plus gros groupe est « autre » ne pilote rien.

32. **Un livrable commercial qui n'a pas l'air officiel doit le dire dans SA PHRASE.** Un BC Adventum émis sans papier en-tête, sans adresse de siège, sans RC ni NIF : le code le savait (`surPapierEnTete: false`, « Identité de l'émetteur incomplète »), et le disait dans un champ JSON pendant que la phrase annonçait « pièce inscrite au registre Legal ». C'est la phrase qu'un modèle reprend — donc on remettait un document générique en le présentant comme fini. La réserve entre dans la phrase, avec le geste EXACT qui la lève, et se tait quand les deux faits sont en règle : une réserve permanente devient du bruit, et on cesse de la lire.

33. **Une étape que le nouveau plan REPREND doit être réarmée — sinon le plan est mort-né.** « Une étape déjà terminée n'est pas réécrite » protège un ACQUIS : un envoi parti ne repart pas. Appliqué à un ÉCHEC, le même `update: {}` tue la mission. Mesuré : deux envois échouent, le plan v2 les reprend et accroche ses six attentes dessus ; l'upsert laisse les lignes en FAILED ; une étape FAILED ne se termine jamais, ses dépendantes ne deviennent jamais READY, et un plan de **18 étapes, profondeur 12, n'a PAS UNE racine exécutable**. Le moteur a repris la main, n'a rien trouvé, et `deduireEtat` a rendu BLOCKED — honnêtement, sur un plan mort-né : 0 réveil, 0 attente levée, 0 livrable, et pas une ligne disant pourquoi. Reprendre une étape dans un plan, c'est demander qu'elle soit RE-tentée : statut, tentatives et motif repartent à zéro, la clé d'idempotence RESTE (une étape peut échouer après avoir produit son effet ; c'est le reçu qui empêche le doublon, pas le statut). Et un `BLOCKED` déduit dit désormais ce qu'il a lu : combien d'étapes en échec définitif barrent la route à combien d'étapes en attente (§118.31).

34. **Une entrée « qui » n'arrive pas toujours en chaîne.** `resolve_person` rend `{ nom, adresse, source, detail }` ; un éventail déploie cet objet tel quel sur `recipientName` ; le lecteur appelait `asStr`, obtenait `""`, et refusait « Destinataire «  » introuvable » sur une personne dont il tenait le nom ET l'adresse. Deux collègues n'ont jamais reçu leur demande. Même famille que « Nom <adresse> » refusé alors que l'adresse était là (§118.21) : un « je ne peux pas » artificiel, où rien ne manquait. `personnes/designation.ts` — module PUR au socle, parce que la conversation ET le moteur en ont besoin sans avoir le droit de se parler (§118.16) — TRADUIT au lieu de refuser, rend `null` sur ce qu'il ne lit pas à coup sûr, et un refus montre désormais ce qu'il a REÇU au lieu d'un vide trompeur. Il ne devine jamais : une liste d'UN candidat désigne cette personne, une liste de PLUSIEURS n'en désigne aucune — la collapser choisirait un destinataire à la place d'un humain. Et `resolve_person` porte maintenant `retenu` : la personne sur qui AGIR, un élément quand c'est certain, liste VIDE sinon — parce qu'un plan qui déployait son envoi sur `candidats` écrivait par chance à la bonne personne tant qu'il n'y en avait qu'une, et aurait écrit à trois homonymes le jour où il y en a trois.

35. **Ce qu'on vient de produire, on le RÉFÈRE ; on ne le cherche pas.** Le plan a inventé un titre — « Consolidation Nivolex–Trastuzex — 08-09-2026 » — et l'a cherché dans le Drive pour « vérifier » ses livrables. Le fichier s'appelle `Consolidation_Nivolex_Trastuzex.xlsx`. Zéro résultat, lu comme une absence : *« contradiction relevée : les recherches Drive des titres finaux n'ont retourné aucun résultat »*. Deux pièces présentes, complètes, portant 6/6 des chiffres collectés, et la mission conclut que son propre travail n'existe pas — trois replanifications, 0,30 $, statut BLOCKED. C'est la règle 21 (« ne relance pas une recherche pour une réponse déjà en main ») appliquée aux pièces, ET le défaut Radia (NOT_FOUND n'est pas ABSENCE_VÉRIFIÉE) réimporté à l'intérieur d'un plan. L'étape ARTIFACT rend déjà `driveNodeId`, `fileName`, `artifactId`, `format`, `byteSize` : la règle 22 du planificateur dit d'écrire `{{produire:excel.driveNodeId}}` — l'identifiant exact, qu'on tient déjà.

36. **Deux mécanismes du même dépôt ne doivent pas diverger sur l'IDENTITÉ d'une pièce.** `identiteDuLivrable` (#88) fait exprès de garder la clé d'ORIGINE quand un replan renomme un livrable : c'est ce qui réécrit le fichier au lieu d'en créer un second. `artefactsAttendus`, lui, lisait les clés du DERNIER plan. Après un renommage (`excel-consolidation` → `excel-consolidation-final`), le contrôle ne pouvait plus PASSER : « 2 livrable(s) annoncés ne sont pas produits » sur deux fichiers vérifiés. Un contrôle arithmétique qui ne peut plus passer est aussi nuisible que celui qui ne peut pas échouer (§118.17), et pire : il bloque une mission juste. Le raccord se fait par le lien CAUSAL — `MissionArtifact.stepId` — jamais par ressemblance de noms : la pièce écrite par l'étape `fromStep` satisfait l'attente que cette étape devait honorer, et une pièce périmée pointe vers l'ancienne étape, donc ne satisfait rien.

37. **Un livrable se produit UNE fois, quand les données sont là (§88).** Le plan écrivait deux étapes ARTIFACT au même format — un dossier Word AVANT les réponses, un second APRÈS, le second descendant du premier. En base : deux fichiers, 1 519 et 2 735 octets ; le premier ne portait AUCUN des chiffres collectés — il ne pouvait pas, ils n'étaient pas encore arrivés. Le dirigeant se retrouvait avec un brouillon et un livrable, sans rien pour les distinguer. Le critère de refus n'est PAS « deux pièces du même format » — deux contrats, deux comptes rendus sont légitimes : c'est la DESCENDANCE. Quand la seconde dépend de la première, la première n'est pas un livrable mais un état intermédiaire, et un état intermédiaire est un WORKER, qui porte le résultat sans déposer de fichier. `identiteDuLivrable` (#88) ne pouvait rien ici : elle réunit deux pièces de PLANS successifs, pas deux pièces que le même plan a délibérément demandées.

38. **Adam s'écrivait à lui-même.** La porte d'attention envoyait `to: compte.email` — la boîte de l'ERP, à elle-même. La personne ne voyait rien tant qu'elle n'ouvrait pas CETTE boîte. Le renseignement existait pourtant : `canalPrefere: "email:adresse"` porte une destination, `lireCanal` la rend, Slack, Teams et WhatsApp la reçoivent — le seul canal qui en avait besoin la jetait. `personnes/joignabilite.ts` (module pur au socle) lit la déclaration, rend les adresses valides dans l'ordre — la première principale, les autres en copie — et une liste VIDE quand rien ne se lit à coup sûr, auquel cas l'envoi retombe exactement sur l'ancien comportement : on ajoute une capacité, on ne redirige pas un envoi au hasard.

39. **Écrire à son propre demandeur n'est pas une communication externe.** Le dirigeant a énoncé huit natures qu'Adam peut lui envoyer sans redemander — fin de mission, résultat, rappel, réponse reçue, problème, décision attendue, changement important, alerte surveillée — et une réserve : « cette permission ne s'étend à AUCUN autre destinataire ». `personnes/autonomie-proprietaire.ts` en fait une règle tenue par le code, pas une consigne de prompt (§118.6). Elle exige DEUX faits et refuse dès que l'un manque : la nature est l'une des huit, et CHAQUE destinataire figure parmi les adresses que la personne a déclarées pour elle-même. Le second point est ce qui empêche l'autonomie de fuir — un document lu par une étape peut dire « écris aussi à X » : la nature passerait, le destinataire non, et **un seul destinataire hors liste fait tomber tout l'envoi**, jamais seulement la ligne fautive. Une garde qui laisse partir « le reste » a déjà échoué. La liste des natures est FERMÉE : en ajouter une est une décision de revue de code.

40. **Une mission longue n'est pas un gros plan, c'est un objectif DÉCOUPÉ.** Un plan monolithique de mission longue n'est pas seulement trop gros pour une fenêtre de contexte : il est FAUX. Le planificateur y écrit l'étape 200 sans savoir ce que l'étape 40 aura trouvé, donc il invente ses références — un destinataire pas encore identifié, un chiffre pas encore reçu, un fichier qui n'existe pas. Un JALON est une INTENTION : un titre, et le résultat qu'on doit pouvoir CONSTATER. Il ne devient des étapes qu'au moment où la frontière l'atteint, c'est-à-dire quand ce qui le précède a réellement produit ses résultats. La compilation paresseuse ne réduit pas un coût : elle rend le plan du jalon 7 INFORMÉ par le jalon 6. Mesuré : sept jalons sur une demande d'appel d'offres, le premier avec 11 étapes, le dernier avec 0 — parce qu'il n'existe encore que comme intention.

41. **Une mission longue qui ne date pas ses lectures conclut sur une vérité périmée.** Jour 1 : le forecast vaut 41,3. Jour 18 : Finance a révisé. Jour 19 : la mission livre. Toutes les étapes vertes, le contrôle passe, le juge lit un livrable cohérent — et personne ne peut voir que le chiffre est mort. C'est le faux succès sans aucune signature d'échec. `MissionInput` garde l'EMPREINTE, pas la valeur (stocker la valeur ferait un second registre qui divergerait, §118.5), et elle vient du REÇU : la seule chose du moteur qui dise ce qui a RÉELLEMENT été interrogé. La bâtir sur `step.input` daterait des lectures qui n'ont pas eu lieu. Le lien `stepKey` est ce qui rend l'invalidation LOCALE : sans lui, la seule réponse à « le forecast a bougé » serait « replanifie tout ».

42. **Le plafond GLOBAL de replans est mort ; ce qui arrête la boucle est le PROGRÈS.** `PLANS_MAX = 4` bornait la MISSION ENTIÈRE : sur sept jalons, un seul qui s'y reprend à quatre fois consommait le budget des six autres, et la mission mourait pour une difficulté locale déjà résolue. Le compteur était aussi aveugle au CONTENU — il comptait pareil un planificateur qui répare quelque chose à chaque tour et un planificateur qui remet le même plan devant le même mur. Ce qui décide maintenant : tant que le refus CHANGE, un tour de plus vaut son prix ; dès qu'il REVIENT identique, c'est fini. `Mission.replanBloque` porte ce verdict et c'est la REQUÊTE du battement qui le lit — la fin est une propriété de la base, pas une discipline. Et il se remet à FAUX dès qu'une information neuve arrive : réponse humaine, reprise après pause, modification demandée. Un compteur ne savait pas distinguer « il tourne en rond » de « on ne lui a rien donné de neuf ». Le plafond survit, LOCAL et opérationnel (§118.2) : par jalon dans `horizon/budget.ts`, `PLANS_MAX_PLAT` pour une mission sans jalons.

43. **Ce qui est destructeur se borne au périmètre de ce qu'on compile.** `materialiser` marque « contournée » toute étape absente du plan qu'on lui donne — juste pour un plan de mission, ruineux pour un sous-plan de jalon : compiler le jalon 2 marquerait contournées toutes les étapes du jalon 1, et la mission perdrait son propre acquis à chaque jalon franchi. `opts.milestoneId` borne le contournement ET le réarmement ; les identifiants d'étapes, eux, restent lus sur TOUTE la mission, parce qu'un sous-plan a le droit de dépendre d'un acquis d'un jalon précédent. Deux questions, deux listes.

44. **« Ce jalon est fini » n'est pas « la mission est finie ».** Sur une mission longue, les étapes en base sont celles du ou des jalons COMPILÉS. Toutes terminales signifie « ce sous-plan a fini », rien d'autre. Sans la porte `horizonOuvert` dans `conclure`, une mission de sept jalons se ferait juger au bout du premier : le juge lirait l'objectif ENTIER, ne verrait qu'un septième du travail, refuserait — honnêtement — et six jalons ne seraient jamais écrits. C'est le faux ÉCHEC symétrique du faux succès de §118.10, et il coûte exactement aussi cher.

45. **Un état qu'aucun code ne lit est une promesse d'écran.** `MissionStatus.PAUSED` existait depuis toujours et RIEN ne l'honorait : on posait le statut, le battement reprenait la mission au tour suivant comme si de rien n'était. Il est lu maintenant à deux endroits, et il en fallait deux : le MOTEUR (`avancer`) pour ne plus exécuter d'étape, et le PILOTE d'horizon pour ne plus PAYER de sous-plan. Un seul des deux aurait laissé une mission suspendue continuer à dépenser du modèle. La pause porte aussi sa date, son motif et l'état qu'elle a interrompu — sans quoi l'écran ne peut pas dire depuis quand, et la reprise ne peut que deviner d'où repartir. Symétriquement, `annuler` ferme les JALONS vivants : sans cette ligne, `horizonOuvert` resterait vrai pour toujours et le pilote reprendrait indéfiniment une mission que quelqu'un a explicitement arrêtée.

46. **La requête qui dit « qui peut avancer ? » doit voir la mission longue ENTRE deux jalons.** Mesuré en live : jalon 1 compilé, ses onze étapes toutes terminées, jalons 2 à 7 pas encore compilés — donc ZÉRO étape PENDING ou FAILED, et un statut RUNNING qui n'est pas replanifiable. Aucune branche de la requête ne la voyait. Le battement ne la reprenait jamais et la mission mourait à son PREMIER jalon : toute la compilation paresseuse était écrite, testée, et sans effet en production (§118.14). C'est l'état NORMAL d'une mission longue, pas une anomalie — un jalon vivant EST du travail à faire, il n'a simplement pas encore d'étapes.

47. **On ne s'arrête pas à la première difficulté — au niveau du JALON aussi.** Le moteur réessayait les ÉTAPES ; personne ne réessayait le jalon. Un jalon passé BLOCKED (étapes épuisées, ou résultat non constatable) y restait pour toujours, sa descendance n'était jamais libérée, et la mission mourait sur une difficulté locale qu'un sous-plan différent aurait contournée. La reprise est un REPLAN, pas un re-run : le jalon repasse à `planVersion: 0` et un sous-plan NEUF est écrit, informé de ce qui a échoué (`refusPrecedent`). Le budget reste local et se juge au progrès, la signature étant l'ensemble des CAUSES d'échec — pas les clés d'étapes, qui changent à chaque plan.

48. **L'empreinte d'une modification de mission ne dépasse jamais la demande.** « Finalement Amel à la place de Deepak » touche les étapes où Deepak est NOMMÉ et leur descendance — jamais l'autre collecte. « Annule uniquement le PowerPoint » ne prend que sa branche EXCLUSIVE : un nœud qui garde un parent vivant hors de l'ensemble sert encore à quelque chose, et l'envoi final survit parce qu'il porte aussi le classeur. Deux axes, jamais confondus : la PROFONDEUR (visée seule, ou descendance) et la CARDINALITÉ (une cible nommée, jamais « tout ce qui lui ressemble » — TOUS les mots utiles doivent être présents). Une cible reconnue nulle part ne touche à RIEN et le dit : deviner choisirait la branche à jeter à la place d'un humain (§118.15). Et ce qui est DÉJÀ parti est NOMMÉ, jamais rejoué — mesuré en live : 16 étapes sur 50 invalidées, 32 préservées, 2 effets irréversibles exclus, et les reçus identiques avant et après.

49. **Un test qui vérifie le CORPS d'une fonction sans vérifier son APPELANT ne teste rien.** Mesuré, et c'était mon propre défaut : `daterLEntree` était écrite, commentée, et couverte par un test qui lisait son corps. Son appel avait été perdu dans une édition. Résultat sur un run live : 53 étapes abouties, 2 332 reçus en base, ZÉRO entrée datée. Le test passait au vert sur du code mort — exactement §118.14, et le test lui-même en était complice. Un test d'architecture qui affirme qu'un mécanisme existe doit chercher son POINT D'APPEL, et à l'endroit exact où il doit être.

50. **Une vue parfaite que rien n'affiche est du code mort — §118.14 appliqué à l'ÉCRAN.** `VueMission.horizon` était calculé, commenté, couvert par ses tests… et AUCUN écran ne le rendait : la page d'une mission de sept jalons montrait « 4/5 étapes », c'est-à-dire les étapes du sous-plan courant, donc « presque fini » sur six semaines de travail restant. `listerAccordsMission`, écrite POUR un écran, n'avait aucun appelant de production : un accord ne se donnait qu'en arrivant par le lien d'une notification, une mission à la fois. Et une mission d'exécution avait une adresse (`/missions/<id>`) sans aucune LISTE — le lien « Toutes les missions » menait au module RH, qui ne la contiendrait jamais. Le critère n'est pas « la vue rend le bon objet », c'est : *une personne qui utilise le produit normalement peut-elle le VOIR, et agir dessus ?*

51. **Un tableau de bord ment par son DÉNOMINATEUR, et il ment en silence.** Quatre façons, toutes mesurées : compter un MODÈLE d'éventail pour un (« 2/2 » sur trente-trois envois dont deux ont raté) ; garder les étapes d'un plan PÉRIMÉ, ce qui fait RECULER l'avancement à chaque replanification ; prendre les étapes du sous-plan courant pour l'avancement d'une mission LONGUE ; et confondre ABOUTI avec FRANCHI — un jalon écarté comme sans objet est derrière nous sans avoir été accompli, et l'écran affichait « 1/4 » sous une jauge à 50 %. Les deux vues (le parc et la mission) calculent désormais la même chose, et un test les compare : deux écrans qui comptent séparément divergent, toujours.

52. **Un filtre dont le défaut est « cacher » rend muet ce que le moteur apprendra à dire.** Le journal brut est majoritairement de la comptabilité de moteur — 8 751 « le moteur prend la main » sur la base de banc, contre six lignes qui expliquent où la mission en est. L'afficher tel quel ne montre rien ; le filtrer par liste blanche rendrait invisible, en silence, chaque genre d'événement ajouté ensuite. Donc : le BRUIT est nommé (liste fermée, courte), un genre inconnu s'AFFICHE, et ce qui a été écarté est COMPTÉ à l'écran — un filtre silencieux ne laisse aucune trace de ce qu'il retire.

53. **Une modification se LIT avant de s'appliquer.** « Finalement Amel à la place de Deepak » a une empreinte exacte : les étapes visées, leur descendance, les jalons rouverts, ce qui est PRÉSERVÉ, et ce qui est DÉJÀ PARTI et ne sera donc pas rejoué. Appliquer d'abord et raconter ensuite demanderait de faire confiance à un résumé écrit après coup ; l'aperçu est donc une action à part qui n'écrit RIEN (vérifié en base par le banc, pas seulement à l'écran), et « Appliquer » n'apparaît qu'après un aperçu dont la cible a été reconnue. Sur une mission qui a déjà sollicité trois personnes, se tromper de branche coûte ces trois demandes, et rien ne les reprend.

54. **« Le fichier s'ouvre » n'est pas « le fichier est livrable ».** Un Word, un PowerPoint ou un PDF produit par une mission était contrôlé ainsi : plus de 200 octets, et les quatre premiers valent `PK\x03\x04` (ou `%PDF`). C'est vrai d'une archive VIDE. Passaient donc en `VERIFIED` — le seul statut qui vaut preuve d'achèvement (§118.10) — un document sans un seul paragraphe, une présentation sans diapositive, un PDF sans page, et surtout un contrat portant encore « [à compléter] », « XXX » ou « {{client}} ». Les quatre partent chez quelqu'un ; le dernier est le pire, parce qu'il s'ouvre, s'imprime, a l'air fini, et le trou est dedans. Le livrable est maintenant OUVERT par l'adaptateur de production, modélisé, et soumis à `controlerAvantLivraison` — le MÊME contrôle que celui qui répond « est-ce que je peux l'envoyer ? » quand une personne édite un document (§118.5 : en écrire un second donnerait deux exigences de qualité selon l'origine du fichier, et celle des missions prendrait du retard). Ce que le rapport dit n'est plus une taille : c'est « 3 paragraphes non vides », « 5 diapositives », « 2 feuilles ». Et un format qu'on n'ouvre pas le DIT (§34) au lieu de se déclarer vérifié.
55. **Une donnée n'a pas seulement une PROVENANCE, elle a un ÂGE — et rien ne s'en souvenait.** `FaitCalibrable` portait `fraicheur` et `horodatage` depuis le début : déclarés sur l'interface, lus par personne. Un fait extrait d'une copie indexée il y a six mois avait `base: "metadata"` et une confiance de 0,95 ; il sortait donc CERTAIN → AGIR, annoncé « FAIT VÉRIFIÉ », et Adam proposait de résilier sur une clause que la source avait pu réviser depuis. C'est §118.46 un cran plus haut : là c'était une mission de trois semaines qui concluait sur un forecast périmé, ici c'est une seule phrase de conversation. **PÉRIMÉ est un ÉTAT, pas un degré de confiance** (§118.16 : la profondeur et la cardinalité ne se confondent pas, l'âge et la provenance non plus) : sur une provenance faible on CHERCHE ailleurs, sur une donnée vieille on RELIT la même source — deux conduites, deux gestes. Trois conditions, toutes nécessaires, et la moitié de la règle est dans ce qui NE périme pas : il faut une COPIE (une lecture en temps réel ne périme pas de la date de sa donnée — une facture de 2024 EST de 2024, la table était vivante), une date qui se LIT (sans elle on ne déclare rien : une garde qui refuse ce qu'elle ne comprend pas est désactivée dans la semaine, §118.16), et un dépassement du seuil de sa NATURE (un chiffre financier tient un jour, un document trente ; un seuil unique serait faux dans les deux sens). Les durées vivent au socle (`src/lib/fraicheur/ages.ts`, zéro import) parce que la conversation et le moteur de missions en ont besoin sans avoir le droit de se parler — deux tables auraient divergé (§118.5). Trois corollaires tenus par des tests : un CALCUL hérite de la fraîcheur de sa PIRE entrée comme il héritait déjà de sa confiance et de sa date la plus ancienne — les trois vont ensemble, la troisième manquait et un total bâti sur une copie de mars se déclarait « temps réel » ; il se juge ensuite sur le budget le plus LARGE, parce que `faitCalcule` ne garde pas la nature de l'entrée qui gouverne et qu'annoncer périmé un total de deux jours ferait du bruit qu'on cesse de lire (§118.32) ; et l'avertissement atteint la CARTE d'action, pas seulement la trace — la trace se déplie, la carte est ce qu'on confirme.

56. **Une ESTIMATION portait la même étiquette qu'une lecture de l'ERP — « FAIT VÉRIFIÉ ».** `faitCalcule` donne à un total la PIRE confiance de ses ENTRÉES ; les entrées d'une simulation sont des LOIS, pas des faits, donc `Math.min()` d'une liste vide, donc **1**. Un P90 de Monte-Carlo et une prévision de série sortaient avec `base: "calcul"` et une confiance de 100 % : CERTAIN → AGIR. Le moteur, lui, le savait — il écrit ses hypothèses, ses limites et ses avertissements à côté du chiffre, et l'en-tête de `calcul-tools.ts` dit en toutes lettres qu'« un P90 sans le nombre de tirages est un chiffre qui a l'air sûr ». **C'est la calibration qui le contredisait**, avec le seul mot que la personne lit vraiment. La ligne de partage n'est ni le moteur ni le déterminisme — une simulation à graine fixe est parfaitement rejouable : c'est que **le calcul dit ce que les données CONTIENNENT, l'estimation ce qu'elles SUGGÈRENT** sous des hypothèses déclarées. Une somme d'écritures réglées, une régression sur des points observés, un chemin critique décrivent ce qui EST ; un tirage et une prévision décrivent ce qui n'a pas encore eu lieu. `base: "estimation"` porte la distinction, et **c'est l'APPELANT qui la pose** : le moteur ne voit qu'un nombre, et le laisser deviner ferait passer un P90 pour un total. La confiance ne rachète RIEN ici — elle mesure la qualité du modèle, pas la vérité du monde, et cent mille tirages ne transforment pas une projection en mesure. Corollaire du maillon faible (§118.55) : une estimation dans un lot de douze chiffres certains gouverne le lot, parce que c'est elle qu'on aurait citée sans le savoir.

57. **Trois gardes disaient déjà « ce que tu affirmes, tu ne l'as pas vérifié » ; il en manquait deux, et un extrait de conversation réelle les a nommées.** `gardeImpossibilite` refuse un « je ne peux pas » que rien n'a vérifié, `gardeAbsence` un « rien trouvé » après une seule façon de chercher. **(a) UNE PROMESSE SANS OBJET DURABLE.** « Je t'avais dit de me rappeler quand t'as des réponses mais tu l'as pas fait » — « Tu as raison : aucun rappel ni suivi conditionnel n'était planifié. » Adam avait dit oui ; rien n'avait été créé ; aucune étape en échec, aucun signal. Une promesse qui ne vit que dans une phrase meurt à la fin du tour, et c'est le faux succès le plus coûteux parce que la personne, elle, ARRÊTE d'y penser. Cinq outils la font survivre — `plan_reminder`, `watch_entity`, `run_mission`, `record_commitment`, `record_decision` — et la liste est FERMÉE : ouverte, n'importe quelle lecture passerait pour un suivi. Sans l'un d'eux : créer l'objet, ou DIRE « je ne pourrai pas revenir vers toi tout seul ». Pas de troisième issue. **(b) « FAIT VÉRIFIÉ : aucun X ».** La plus forte étiquette posée sur ce qu'on n'a PAS vu. Cette phrase-là était juste — la table des rappels fait foi sur son propre contenu — mais rien dans le code ne le savait au moment de l'écrire : la même phrase après une recherche dans l'index de contenu aurait porté la même étiquette et aurait été fausse. `DescripteurSource.preuveNegative` le dit source par source depuis toujours (« pas dans l'index » n'est pas « pas dans le Drive »), et chaque fait du tour le porte ; il ne restait qu'à le LIRE avant de laisser passer le mot. Deux différences avec les trois autres, et elles comptent : celle-ci ne fait pas recommencer le tour — le travail est fait, c'est le MOT qui est trop fort, et refaire coûterait un aller-retour pour rien (§118.27) ; et elle a son PROPRE détecteur d'absence, plus large que celui de `gardeAbsence` — élargir le premier ferait relancer une recherche sur « aucun rappel n'était planifié », une phrase qui ne demande rien de tel. Deux questions, deux détecteurs ; les confondre casserait l'une des deux gardes.

58. **Réparer quinze capacités à la main ne protège pas la seizième — et surtout pas celle qu'ADAM crée.** §118.20 recensait onze sorties dont la FORME changeait selon la donnée ; elles ont été réparées une à une, plus quatre trouvées en chemin. La bonne objection est venue en cours de route : le cœur n'est pas modifié pour qu'un skill existe (§36 — micro-outil promu, connecteur déclaré par manifeste, playbook enseigné), donc il n'y a AUCUN endroit où aller corriger la forme d'une capacité qu'on n'a pas écrite. Deux couches, et il faut les distinguer sans les confondre : les accesseurs INTERNES à l'ERP portent le filtrage RBAC (`scopeRegulatory(user)`, `canViewDrive`) et un modèle n'a pas le droit de les écrire — c'est §118.6 et §118.7, pas une lacune ; les capacités DYNAMIQUES, elles, sont créées sans nous, et c'est l'intention. Ce qu'un skill DÉCLARE, en revanche, le code peut le vérifier : `sorties.cles` vivait dans le manifeste depuis le début, servait à décrire l'outil au modèle, et n'était comparé à RIEN. Une capacité pouvait donc annoncer `{ montant, devise }` et livrer `{ erreur }` — le défaut de §118.20, du côté où l'on ne peut pas éditer le code fautif. `skills/contrat-sortie.ts` (pur, au socle) le CONSTATE à chaque exécution et le fait voyager avec la sortie. Il ne comble pas : ajouter les clés manquantes à `null` fabriquerait une sortie que la capacité n'a jamais produite, et le plan croirait tenir une valeur — un faux succès strictement pire que l'écart. Il ne refuse pas non plus l'appel (§118.27). Et il se tait sur un échec annoncé, sur un contrat vide, et sur tout résultat qu'il ne lit pas à coup sûr (§118.16). Ici la catastrophe n'a pas eu lieu — le réseau du conteneur bloque le port 5432 sortant, vérifié — mais le trou était dans le CODE, pas dans le pare-feu, et un poste de développeur qui atteint sa base de production l'aurait payé.

91. **Un banc partagé n'est pas reproductible, et son semis détruisait sa propre poignée.** Le retrait par IDENTITÉ trouve une ligne par son AUTEUR ; or supprimer un compte NULLIFIE ce lien (`onDelete: SetNull`) au lieu de supprimer la ligne. Mesuré : 78 `RegulatoryProduct` sans auteur, dont les huit références du semis — introuvables par le critère même qui les aurait trouvées, et le semis suivant échoue sur une contrainte d'unicité dont la cause est invisible. C'est le nettoyage qui effaçait son manifeste (§118.52), un cran plus bas. On ne referme pas ça par une liste de clés uniques écrite à la main — le schéma en porte quatre-vingts, et une liste manuelle est fausse au premier ajout, en silence (§118.73). On cherche l'endroit où TOUTES les instances passent (§118.58) : la base. `--reset` vide les 314 tables et resème (mesuré : 107 lignes, 9 comptes), la garde de base étant REDEMANDÉE juste avant le `TRUNCATE` — une opération destructrice porte sa propre raison, elle ne l'emprunte pas à son appelant. **Corollaire mesuré** : quatre bancs cherchent `role: "SUPER_ADMIN"`, dont un par `createdAt: "asc"` ; dans une base partagée ils tombaient sur un administrateur de PRODUCTION. Le banc mesurait avec une identité étrangère à sa propre vérité terrain. Il a désormais son compte technique, créé en premier, sur son domaine.

92. **Trois échecs sur quatre étaient ceux du JUGE, et il a fallu ouvrir la base pour le savoir.** Campagne complète : 44/48 au premier passage. **(a) « Une simulation n'écrit RIEN »** comptait `createdAt >= ctx.t0`, un `Date` JS (milliseconde) contre un horodatage Postgres (microseconde) : la dernière ligne du décor, insérée dans la même milliseconde que la prise de `t0`, était comptée comme écrite par Adam. En base : 30 lignes, toutes du décor, zéro écriture du tour. On COMPTE avant/après, aucune horloge dans la comparaison. **(b) Le briefing de chef de cabinet** disait « caisse d'avance GELÉE jusqu'à ce point budget T3, décidée le 12/08 » — l'historique exact que le défi réclame — et le juge cherchait `/geler|gel /i`. Un défi parfaitement réussi compté en échec sur une flexion française. Le juge lit désormais le FAIT (radical `gel` ET « caisse » dans la MÊME ligne, accents pliés), ce qui écarte au passage « gélule », mot de tous les jours dans cet ERP. **(c) « Rien avant la signature »** comptait les tâches dont le TITRE contient « Mouffok » : au run suivant, une mission du run PRÉCÉDENT — qui avait reçu sa signature vingt-cinq minutes plus tôt — a fait tomber le défi. En base : la mission du tour est `WAITING_EVENT`, son étape `create_task` est `PENDING`, et la tâche incriminée porte l'horodatage de l'étape d'une AUTRE mission. On juge par le lien CAUSAL — l'étape de CETTE mission — jamais par ressemblance de noms (§118.36). **La leçon de méthode** : devant un échec de banc, la première question n'est pas « qu'est-ce qui est cassé dans le produit ? » mais « qu'est-ce que le juge a réellement mesuré ? ». Trois fois sur quatre ici, la réponse était « autre chose ». Et le quatrième — `defi-finance-signaux`, un signal sur deux rapporté — s'est révélé de la VARIANCE : au tour suivant, trois appels de `finance_intelligence` au lieu d'un, et les deux signaux cités. Deux runs live ne se comparent pas comme deux exécutions d'un test (§118.66).

93. **Un outil qui ne sait pas EXPRIMER une question la rend en impossibilité.** « Combien d'heures de réunion ai-je eues ces 30 derniers jours, et avec qui le plus souvent ? » → « INCONNU — le calendrier Google d'ADAM n'est pas connecté ; aucune donnée de réunions sur les 30 derniers jours n'est donc lisible. » **Faux deux fois** : l'ERP a son propre agenda, et `getCalendarEvents(user, from, to)` — la lecture par FENÊTRE — vivait dans le MÊME fichier que l'appel qui ne s'en servait que pour un seul jour. `read_calendar` n'offrait que « un jour » ou « la suite » ; sa description ne nommait que le futur. La capacité était à un argument près, et le modèle a envoyé le dirigeant brancher un service tiers pour rien : NON TROUVÉ annoncé comme SOURCE ABSENTE (§118.63, et le défaut Radia à nouveau). L'outil porte maintenant une PÉRIODE passée comme future, une durée par événement **seulement quand la fin est connue** (prêter soixante minutes fabriquerait un total qui a l'air juste, §118.16), un récapitulatif CALCULÉ par le code — total, classement des personnes — et le COMPTE de ce qui n'a pas pu être totalisé. Et l'absence se DIT comme une absence : « aucun événement dans l'agenda de l'ERP du … au … — c'est une ABSENCE constatée, pas une source indisponible. » Pourquoi pas `sql_query` : `CalendarEvent` n'est pas dans `TABLES_AUTORISEES`, et ce n'est pas un oubli — un agenda porte des rendez-vous privés et son cloisonnement se calcule par LIGNE. On étend l'outil qui PORTE la portée, jamais la porte générique (§118.85). Mesure : 6,7 s et 0,029 $ au lieu de 22,3 s et 0,10 $, avec une réponse au lieu d'un refus.

94. **Deux transcripteurs dans le même dépôt, et seul l'un des deux se souvient.** `defi-media-reunion` : Adam a répondu JUSTE — instants et citations conformes au mot près à l'enregistrement — sous l'étiquette « FAIT VÉRIFIÉ », et `MediaTranscript` était VIDE. Le texte horodaté vivait dans `DriveTextIndex`. Cause : `transcrireMediaDrive` est idempotent, persiste segments, modèle et méthode, et alimente `media_transcript action=chercher` ; `extractAttachmentText` — la porte qu'un modèle emprunte naturellement via `read_document` — refait l'appel de parole à CHAQUE lecture et ne garde rien (§118.5, et c'est la version oublieuse qui gagne parce qu'elle est sur le chemin naturel). Trois conséquences nommables : on paie la transcription autant de fois qu'on lit ; l'outil FAIT pour « où exactement en parle-t-on ? » reste aveugle à une transcription déjà faite ; la MÉTHODE et la CONFIANCE d'une lecture de parole ne sont plus persistées. **Et le second défaut était pire que le premier** : `lireMedia` écrivait une réserve exemplaire — « ce n'est pas un fait vérifié : à citer comme PROBABLE, avec l'instant » — que `read_document` passait à l'INDEX puis JETAIT. La seule phrase qui contredisait « FAIT VÉRIFIÉ » n'a jamais franchi la porte. Un média du Drive passe désormais par le transcripteur qui persiste (mesuré : `whisper-1`, 9 segments horodatés, locuteurs attribués, contre 0 ligne avant), la note de méthode VOYAGE avec le texte pour tout format, et l'échec de transcription retombe sur la lecture d'octets — ajouter une capacité ne doit pas retirer celle qui marchait (§118.27).

95. **Un refus de Postgres qu'on peut compléter, on le complète.** `defi-sql-comptage` : le modèle écrit `status = 'SANS_STATUT'`, Postgres répond `invalid input value for enum "TaskStatus"`. Le refus est JUSTE et INUTILISABLE — il nomme la faute et pas le remède, et trois appels de `sql_query` partent sur la même question (§118.30). Les valeurs viennent du DMMF, donc du SCHÉMA : une valeur ajoutée demain est nommée sans que personne y pense. Ce qu'on ne fait PAS : deviner les COLONNES d'un `column "x" does not exist`, parce que le message ne dit pas de quelle table il parle et que proposer les colonnes d'une table au hasard enverrait le modèle réécrire sa requête sur le mauvais objet. Un type d'énumération, lui, est NOMMÉ dans le message : c'est toute la différence entre lire et deviner (§118.16).

96. **Le filet du talon tuait les missions LONGUES — §118.46 avait un second lecteur que personne n'avait mis à jour.** `rattraperLancementsPerdus` cherche « PLANNING + zéro étape + rien depuis deux minutes » et relance la planification, trois fois, puis ferme en `PLANNING_FAILED`. Or **zéro étape est l'état NORMAL d'une mission à jalons** : §118.40 exige que le sous-plan du jalon N s'écrive quand le jalon N-1 a produit ses résultats. Mesuré sur la chaîne humaine, deux runs de suite : `MILESTONES_PLANNED` (cinq jalons), l'enquête tourne, le filet déclare la mission perdue, relance jalons + enquête — payés à chaque fois — et au troisième tour ferme une mission parfaitement saine. Verdict du banc : « FOURNISSEUR INDISPONIBLE : la mission n'a jamais reçu de plan », sur un fournisseur qui répondait « PRÊT » en 1,8 s une minute plus tard — **un banc qui accuse la mauvaise cause avec assurance** (§118.84, §118.92). §118.46 avait appris cette leçon à la requête du BATTEMENT ; ce second lecteur gardait l'ancienne hypothèse. Le fait à lire est le même et il est dans la base : **une mission qui a des JALONS a été planifiée** — ses étapes viennent du pilote d'horizon, qui la reprend précisément parce qu'elle est en PLANNING. Le filet reste ARMÉ sur le vrai cas (ni jalon ni étape), et le test le prouve dans les DEUX sens : sans cette seconde assertion, la garde serait désarmée en ayant l'air armée (§118.17). Mesure : la chaîne humaine passe de 4/12 à 5/12, la mission atteint 20 étapes et plan v4 au lieu de mourir en `PLANNING_FAILED`, l'accord est demandé et donné, et Adam revient vers le dirigeant. **Corollaire de méthode** : quand une règle est apprise à un endroit, la question suivante n'est pas « est-ce corrigé ? » mais « qui d'autre lit ce même fait ? ». Ici il y avait deux lecteurs de « zéro étape », et le second était celui qui pouvait TUER.

## Live Office — la doctrine (§104)

Éditer un document Office n'est pas « générer un fichier ». C'est ouvrir CE fichier, le modifier,
et le refermer en `.docx` — le même, avec ses styles, ses images et ses en-têtes.

1. **On n'ouvre jamais un format qu'on ne sait pas refermer.** Un `.docx` entre et sort en `.docx`.
   LibreOffice a été MESURÉ absent (`libreoffice-core` seul ; Render déploie en `runtime: node`) —
   la décision de ne pas convertir n'est pas un renoncement, c'est ce qui rend une retouche
   instantanée et fidèle.
2. **L'arbre XML garde sa tranche de source.** `object-model/xml.ts` : nœud intact → recopié octet
   pour octet, nœud touché → reconstruit, et lui seul. **Ce que le code ignore, il le préserve.**
   `adapters/fidelity.test.ts` le vérifie à la PIÈCE près, pas « le fichier s'ouvre encore ».
3. **L'état est un rejeu, jamais un instantané.** Version Drive de base + opérations non annulées.
   Annuler = marquer et rejouer. C'est ce qui rend l'annulation exacte pour quatre formats sans une
   seule commande inverse, et la reprise après panne gratuite.
4. **La numérotation est HUMAINE, 1-indexée, partout.** Page 1 = la première. Paragraphe 3 = le
   troisième que la personne VOIT — pas ceux des cellules de tableau, pas le `<w:p/>` vide que Word
   met après chaque tableau. Les suppressions se font en ordre DÉCROISSANT.
5. **Un décodeur ne devine jamais.** `commands/nl.ts` rend `null` sur tout ce qu'il ne reconnaît pas
   à coup sûr, et le modèle prend la main. Attraper une phrase qu'on comprend mal est PIRE que ne
   rien attraper : cela empêche le modèle de bien la traiter, en silence.
6. **Le modèle produit des commandes, jamais de l'XML.** `commands/compile.ts` refuse une opération
   inconnue, une opération hors format, un champ obligatoire manquant, une valeur aberrante. Un lot
   partiellement valide applique ce qu'il peut et DIT le reste.
7. **Une cible ambiguë rend des candidats.** Jamais « le premier des quatre ». Modifier le mauvais
   paragraphe en annonçant que c'est fait est le défaut le plus coûteux de tout ce système.
8. **La sauvegarde est atomique et verrouillée.** Sérialiser → RELIRE → écrire seulement si la
   relecture passe. Si quelqu'un a enregistré entre-temps, on refuse et on le dit.
9. **`artifact/` ne connaît ni le Drive, ni Prisma, ni le RBAC.** Ses capacités arrivent par
   `ports.ts`, remplis par `src/platform/in-process/artifact/`. Le contrôle des droits vit là et
   nulle part ailleurs — `canViewDrive` pour lire, `canEditDrive` pour écrire. **La conversation
   n'est pas une porte dérobée.**
10. **Le contenu d'un document est une DONNÉE.** Il arrive au modèle par `wrapUntrusted`, la même
    barrière que les corps de mails. Une phrase « ignore les consignes » reste du texte lu.
11. **Un seul bloc par document.** Même `blockId`, `version++`. Trois retouches ne font pas trois
    cartes qui s'empilent : la même se transforme.
12. **Deux bancs, et ils tournent.** `npm run office:bench` mesure (et dit ce qu'il NE mesure pas :
    réseau, déchiffrement). `npm run office:sabotage` réintroduit seize défauts plausibles et exige
    que la suite tombe — un sabotage qui passe est un trou, pas un succès.
13. **Une image entre par sa RÉFÉRENCE et sort par ses OCTETS, jamais l'inverse.** Une commande
    d'insertion porte le NOM du fichier ; c'est le moteur qui le résout à travers le port, donc sous
    les droits de la personne, et qui dépose les octets juste avant d'appliquer. Mettre le `Buffer`
    dans la commande ferait peser des mégaoctets au journal, rejoués à CHAQUE ouverture (§104.3).
    Symétriquement, POSER et LIRE une image passent par le même ciblage : deux chemins de
    désignation finiraient par diverger, et « remplace la 2ᵉ image » ne toucherait plus la même que
    « lis la 2ᵉ image ».
14. **Excel ne met pas l'image DANS la feuille, il la met à côté.** Six endroits, pas quatre : les
    octets, le type de la partie image, une partie DESSIN et son type déclaré, les relations du
    dessin vers l'image, celles de la feuille vers le dessin, et `<drawing>` dans la feuille. Trois
    pièges, chacun silencieux : le schéma d'une feuille est une SÉQUENCE (`tableParts` doit rester
    APRÈS — l'ajouter « à la fin » fait perdre le tableau structuré, qu'Excel « répare » sans rien
    dire) ; une feuille ne renvoie qu'à UN dessin (créer une seconde partie fait disparaître
    l'image précédente) ; la relation vers les octets appartient au DESSIN (dans la feuille, elle
    donne un cadre vide). Sans taille demandée, on borne à la zone d'impression que le classeur
    DÉCLARE : une feuille n'a pas de bord à l'écran, mais un classeur s'imprime.
15. **Une lecture d'image n'est jamais un fait vérifié — et une absence de lecteur n'est pas une
    lecture vide.** Le texte et la NOTE de méthode voyagent ensemble : livrer la sortie d'un OCR
    sans dire d'où elle vient la fait citer comme une certitude (§29). Et un composeur sans port de
    vision doit DIRE qu'il ne sait pas regarder : répondre « lu, rien dedans » ferait conclure que
    le tampon est vierge alors que RIEN n'a été tenté — le faux succès parfait. Le contenu lu reste
    une DONNÉE (`wrapUntrusted`) ; la note, qui vient de notre code, reste dehors.
16. **Un cadre gris n'est pas un rendu.** Le workspace dessinait « Image — 4,0 × 2,0 cm » à la
    place de l'image : la personne ne pouvait pas distinguer le logo de 2019 de celui de 2027,
    donc pas VÉRIFIER ce qu'Adam venait de faire — et « c'est fait » redevenait une parole à
    croire, ce qu'aucun écran de ce produit n'a le droit de demander. Les octets servis sont ceux
    de l'état COURANT et non de la version Drive (après un remplacement, l'écran doit montrer le
    nouveau), l'adresse porte l'identifiant de SESSION (le moteur ne rend une session qu'à la
    personne à qui elle est) et la révision (sans quoi le navigateur re-sert l'image d'avant), et
    le type vient de l'EN-TÊTE — un `.png` qui contient du JPEG existe.
17. **Un refus qu'on lit de travers est un refus qu'on croit moins.** « ce document ne contient
    aucun image » est passé en production : le refus était JUSTE, il était simplement écrit dans
    une langue que personne ne parle — et c'est la phrase qu'une personne lit et qu'un modèle
    reprend. Les accords vivent dans `commands/resolve.ts`, la liste des libellés est EXPLICITE, et
    un test d'architecture refuse tout libellé passé à `resoudre` sans genre déclaré : deviner
    d'après la terminaison marcherait sur « image » et échouerait sur « page » comme sur
    « graphique ».

`src/lib/missions/` est déclaré **façade (L2)** dans `src/platform/domains.ts` : il n'importe jamais `assistant/`. Les capacités lui arrivent par un **port** (`missions/ports.ts`), ce qui l'empêche structurellement de s'en octroyer une. Côté Adam, l'accès passe par le **contrat de plateforme** (`mission.status`), jamais par un import direct — `boundary.test.ts` le vérifie.

## Graphify = couche de compréhension principale (OBLIGATOIRE)

Le graphe de connaissance du code (`graphify-out/graph.json`, ~10 200 nœuds / ~1 590 fichiers) est la **carte d'architecture** du projet. Objectif : réduire les tokens et garder la cohérence — on interroge la carte AVANT d'ouvrir le code.

Règles :
1. **Avant toute tâche structurelle ou modification non triviale**, interroger d'abord Graphify :
   - `npm run graphify:query -- "<nœud>"` → explication d'un symbole + ses voisins (ex. `"userCan"`, `"createExpenseOrder"`) ;
   - `npm run graphify:query -- path "A" "B"` → chaîne reliant deux symboles ;
   - `npm run graphify:report` → hubs et communautés (vue d'ensemble).
2. **Lire les fichiers source seulement après** avoir identifié les fichiers pertinents via Graphify.
3. **Pas de recherche large** (grep exploratoire, lectures massives en éventail) avant la requête Graphify. Un grep **ciblé** sur un symbole déjà localisé par le graphe reste permis.
4. **Rafraîchir après chaque gros lot fonctionnel** (nouveau module, refonte) : `npm run graphify:refresh`, puis committer `graph.json` / `graph.html` / `GRAPH_REPORT.md`. **Jamais à chaque micro-commit** (~8 Mo d'artefacts par refresh).
5. Fraîcheur : `GRAPH_REPORT.md` indique `Built from commit`. Si le graphe a plusieurs gros lots de retard sur `HEAD`, le rafraîchir avant de s'y fier.

Fallback autorisé (le graphe ne couvre pas tout) : contenu exact d'un fichier déjà identifié, chaînes littérales / libellés UI, fichiers hors `src/` (`prisma/`, `scripts/`), ou graphe indisponible.

60. **Le rendu qui passe devant un comité était le seul des quatre à se taire.** Le schéma EXIGE des sources du modèle (« au moins une entrée dès qu'il y a des chiffres ») ; le classeur leur donne une feuille, le Word une section, le PDF un bloc — le PowerPoint les jetait, `spec.sources` n'apparaissait pas une seule fois dans `rendrePptx`. Un deck dont on ne peut pas dire d'où vient le chiffre ne se défend pas en séance : c'est la première question posée. Il coupait aussi deux fois en silence — dix lignes sur quarante, quatre feuilles sur douze — là où le Word DIT ce qu'il laisse (« 30 lignes supplémentaires — voir le classeur »). Une coupe silencieuse se lit comme une exhaustivité : le lecteur croit voir le tableau, il en voit le quart (§118.52). La cause n'est pas trois oublis : ce rendu-là a été écrit comme un APERÇU, et c'est lui qu'on projette. Corriger `rendrePptx` répare le cas ; `render-complet.test.ts` répare la CLASSE — il boucle sur les QUATRE formats, donne à chacun une spec plus grosse que toutes ses limites, ROUVRE le fichier avec l'adaptateur de production et exige d'y lire la source déclarée et le compte de ce qui n'a pas tenu. Le prochain format ajouté ne pourra pas recommencer. **Et la cause était plus profonde : il y avait DEUX constructeurs de decks.** `artifact/decks/build.ts` tient les règles éditoriales comme des BLOQUANTS, relit le fichier produit avec l'adaptateur de production et le soumet au contrôle de livraison ; il sert la capacité `artifact.deck_build` d'Adam et la fabrique de dossiers de comité. `rendrePptx` dessinait à la main — et c'est LUI qui produit le deck qu'une MISSION envoie. Ils avaient divergé exactement là où on l'attend : **sept puces d'un côté, six de l'autre**, pour la même règle. Le rendu des missions ne dessine plus rien : il TRADUIT (`artifacts/deck.ts`) vers le constructeur unique, et la traduction ne jette jamais — treize puces deviennent trois diapositives, un paragraphe de trois cents mots devient des CORPS successifs, un tableau de quarante lignes montre ses douze premières EN LE DISANT dans son titre (les notes sont pour le présentateur ; l'assemblée voit la diapositive). Un test pousse chaque borne et exige zéro bloquant : traduire en recopiant ferait partir un fichier VIDE dès qu'un modèle est bavard, c'est-à-dire un refus à tort, pire que le défaut corrigé (§118.27). Gagné au passage, sans une ligne de plus : notes du présentateur, chiffre clé, thème, et un compte de diapositives MESURÉ — `detail.diapositives` valait `1 + summary.length`, faux dès qu'une section débordait.

61. **Une réparation DÉPLACE une donnée ; il faut la retrouver chez tous ceux qui la lisaient.** `promouvoirTotaux` (§118.59) sort la ligne de total des DONNÉES pour en faire une OPÉRATION — juste pour le classeur, qui écrit une formule. Mais le Word, le PDF, le CSV et le deck ne rendent que `rows` et n'avaient JAMAIS lu `totals` : la promotion, seule, faisait disparaître le total de **quatre livrables sur cinq**. Aucun contrôle de structure ne l'aurait vu — le fichier s'ouvre, il est simplement amputé, et c'est le lecteur qui découvre en réunion qu'il n'y a pas de total. Trouvé en relisant mon propre diff avant de le pousser, pas par un test : d'où la règle, qui est une question à poser à chaque fois qu'on déplace une donnée d'un champ vers un autre — *qui lisait l'ancien ?* Les quatre formats sans moteur de formules reçoivent donc la ligne CALCULÉE, et ce qu'ils affichent est meilleur qu'avant, pas seulement préservé : le nombre vient du code et non de l'arithmétique mentale d'un modèle. Le LIBELLÉ (« TOTAL », « MOYENNE ») est commun aux cinq, pour la raison habituelle — deux endroits qui nomment la même ligne finissent par la nommer autrement (§118.5).

62. **Le contrôle avant livraison ne voyait pas DANS les tableaux d'une diapositive.** Une forme PowerPoint ordinaire porte un `p:txBody` ; un TABLEAU (`p:graphicFrame` → `a:tbl`) porte un `a:txBody` par CELLULE, et l'adaptateur ne lisait que le premier `p:txBody` — donc `text: ""` pour tout tableau de diapositive. Le Word inspecte ses cellules depuis toujours ; le PowerPoint ne le pouvait pas. Un « [à compléter] », un « XXX », un « {{client}} » posé dans un tableau franchissait la porte et partait **en comité**, dans le seul format qu'on projette devant une assemblée. La lecture couvre maintenant les deux corps de texte, et le contrôle a été SCINDÉ en conséquence : le reste de brouillon se cherche PARTOUT, les règles éditoriales (six puces, vingt-cinq mots, dix points) ne s'appliquent qu'au TEXTE — douze lignes de tableau ne sont pas « douze puces que personne ne lira », et les confondre remplirait le rapport d'un avertissement par diapositive de données jusqu'à ce qu'on cesse de le lire (§118.32).

64. **Six octets arrêtaient le serveur, et c'est ma propre ouverture qui rendait le chemin atteignable.** `BM????` dans une archive : `sharp` refuse l'en-tête, le code disait « pré-traitement best-effort : on OCR l'image brute si sharp échoue », et donnait ces octets à Tesseract. Dans le second cas ces octets ne sont pas une image, et on ne les présente pas au moteur. On RÉSERVE donc avant de composer (une ligne PENDING, sans fichier, portant l'empreinte des données amont), puis on DÉSIGNE l'auteur de la base : la plus ancienne, à égalité la clé la plus petite. Comme chacun réserve avant de lire, tous voient le même premier — la désignation est identique pour tout le monde, sans verrou. L'attente de la base est BORNÉE et n'échoue jamais : bloquer une mission pour une COHÉRENCE coûterait plus cher que le défaut. Deux garde-fous : le format doit DIFFÉRER (deux livrables de même format sur les mêmes données sont deux découpages voulus, « un classeur par produit »), et une ligne réservée sans octets n'est jamais comptée comme produite — `goal/qa.ts` exige VERIFIED et `byteSize > 0`.

Or le planificateur écrit son champ d'après la forme APPRISE, celle des jours où la capacité TROUVE : le chemin se perdait dans une chaîne, l'étape passait `INVALID_STEP` non rejouable, et TOUTE sa descendance restait PENDING — c'est le défaut `directory_list` de §118.99, une seconde fois, par la porte qu'on n'avait pas regardée. C'est §118.71 au niveau de l'ÉTAPE, et le raisonnement est le même : **un scalaire n'a AUCUN champ, donc la seule valeur qu'il puisse offrir est lui-même** ; le plan demandait « ce que cette étape a produit », l'étape a produit cette phrase, et le WORKER en aval est un modèle qui la lira et la dira. La règle vit à UN endroit que le diagnostic et l'injection lisent tous deux — deux lectures du même fait finiraient par diverger, et le symptôme serait une étape diagnostiquée résoluble qui reçoit `undefined` (§118.5, et c'est le second sabotage). Rien n'est silencieux : `REFERENCE_TRADUITE` consigne quel champ a été demandé et ce que l'étape a répondu à la place — un compte rendu qui parle d'absence doit pouvoir dire pourquoi (§118.52). **(d) Un refus de Postgres qu'on relaie doit porter la CAUSE, pas l'en-tête de l'enveloppe.** `messageCourt` prenait la première ligne non vide d'une erreur Prisma : c'est `Invalid \`prisma.$queryRawUnsafe()\` invocation`, le NOM de l'appel. La cause est la DERNIÈRE ligne. Un délai dépassé et une saturation de connexions se disent maintenant en clair, avec le geste — resserrer la requête, ou réessayer parce que la requête n'a PAS commencé et n'est donc pas en cause. **Et la leçon de méthode, la même que §118.92 :** devant un échec de banc, la première question n'est pas « qu'est-ce qui est cassé dans le produit ? » mais « qu'est-ce que le juge a réellement mesuré ? ». Cinq fois sur cinq ici, le défaut était dans le LECTEUR, le JUGE, la FORMULATION ou l'OUTILLAGE — jamais dans la logique métier.

103. **Le mécanisme écrit pour rendre §118.20 VISIBLE portait le défaut de §118.20.** La forme APPRISE (`MissionStep.result`, §118.53) prime sur toute table écrite à la main, et c'est la seule ligne que le planificateur lit pour savoir sur quoi il peut compter. Or `formeDe` choisissait UNE nature : dès qu'une exécution avait rendu un objet, la forme était OBJET et les exécutions qui avaient répondu par une PHRASE disparaissaient. Une promesse fausse, dans la ligne exacte que le planificateur consulte avant d'écrire une référence, produite par le mécanisme censé signaler ce genre de mensonge. Le comptage est désormais un COMPTE et non un booléen — « 2 fois sur 10 » et « 9 fois sur 10 » ne se planifient pas de la même façon, et un booléen aurait effacé la différence — le dénominateur de `toujours` est le nombre d'OBSERVATIONS, et la ligne DIT la branche « rien trouvé » avec le geste sûr : référencer l'étape ENTIÈRE, que le moteur résout toujours, phrase comprise (§118.102c). **Deux questions, deux dénominateurs** : pour un ÉLÉMENT de liste, « toujours » se juge sur les ÉLÉMENTS et non sur les exécutions — les confondre marquerait occasionnel un champ que chaque élément porte, et le planificateur cesserait d'écrire l'éventail qui marche. Et la réserve se TAIT quand aucune exécution n'est sans champ : une réserve permanente devient du bruit qu'on cesse de lire (§118.32), donc inutile là où elle compte. Le compilateur, lui, ne refuse toujours RIEN sur une forme VALEUR : refuser un plan correct parce qu'une capacité répond par une phrase serait échanger un défaut contre un pire (§118.27). **Leçon de méthode, et elle vaut au-delà de ce fichier** : quand un mécanisme existe pour rendre un défaut visible, il faut lui appliquer le défaut qu'il surveille. Ici, la question « et si les observations n'avaient pas toutes la même FORME ? » est exactement celle que §118.20 pose aux capacités — personne ne l'avait posée à leur observateur.

104. **« Quoi de neuf ? » répondait « je ne peux pas » avec la réponse en base — et c'est le REDÉMARRAGE qui déclenchait le mensonge.** `what_changed` sans référence n'avait qu'UNE source : la projection en MÉMOIRE du processus (`change-feed.ts`), parfaitement honnête sur elle-même — « je ne vois que ce qui s'est passé depuis le démarrage de CE serveur », et son en-tête dit même qu'elle ne fait JAMAIS foi. Le défaut n'était pas dans cette phrase, il était dans le fait qu'elle était la SEULE : flux éteint → « je ne peux pas dire ce qui a bougé à l'instant » ; flux vide → « aucun changement depuis le démarrage de ce serveur ». Or Render redéploie et redémarre le processus, et pendant ce temps `BusinessEvent` — le registre canonique (§17) — porte toute l'activité. Un « je ne peux pas » écrit dans le CODE (§118.59, §118.63), sur l'une des questions les plus naturelles d'un dirigeant, avec la réponse à un fichier de distance : `timelineOf` lit déjà ce registre, il lui manquait seulement de savoir répondre SANS entité. **On ne remplace pas, on FUSIONNE — et c'est une mesure qui l'impose** : les deux sources ne portent pas les mêmes faits (le bus est alimenté par `emit` depuis trois fichiers, le registre par neuf domaines). Ne garder que le registre perdrait les faits du bus ; ne garder que le bus perd tout après un redéploiement. **L'autorité voyage avec chaque fait** (`source: "registre"` fait foi, `source: "flux"` est un indice) : les mélanger sans le dire ferait passer un indice partiel pour une vérité, ce que ce fichier interdisait déjà en toutes lettres. **Le cloisonnement est par ENREGISTREMENT** (`canAccessEntity`), jamais par domaine — filtrer par domaine montrerait le dossier confidentiel d'un service ouvert — et ce qui ne se cloisonne pas à coup sûr est écarté ET COMPTÉ (§118.52). **Et le juge du banc mesurait le VOISINAGE** : la base de travail porte 26 332 faits sur sept jours, 4 356 sur vingt-quatre heures ; un fait de test daté d'hier tombait hors des soixante plus récents et le test échouait sur ma manipulation, pas sur le produit (§118.91, §118.92). Ce comptage a nommé le vrai défaut de conception : rendre « les soixante plus récents » SANS le total ferait lire les dernières minutes comme le bilan de la semaine — une coupe silencieuse se lit comme une exhaustivité (§118.60). Le total voyage donc avec l'échantillon, la troncature se DIT avec le geste qui la lève (resserrer `since`), et la fiche de l'outil dit enfin que `since` sert AUSSI sans référence (§118.19). **Enfin, le sabotage a trouvé une assertion morte, et c'était la garde de permission** : retirer l'appel à `canAccessEntity` ne faisait tomber AUCUN test, parce que l'unique acteur du banc était la DIRECTION, dont l'accès est global — la garde rendait « vrai » quoi qu'il arrive. Un acteur SANS vue globale a été ajouté et le sabotage tombe désormais. C'est §118.17 sur la garde la plus sensible du lot : **une garde qu'on ne peut pas faire échouer est une décoration, et le fait qu'elle protège aujourd'hui par la grâce du filtre de son appelant ne compte pas** — c'est exactement le défaut de §118.71, une porte gardée à côté d'une porte ouverte.

106. **La garde du vide était chez le LECTEUR ; il en fallait une chez l'ÉCRIVAIN.** §118.105a a fermé la lecture — `nodeText` refuse d'honorer un index de contenu vide SANS raison. 107. **Le circuit d'une demande dépendait de qui la POSAIT, et une seule borne manquait pour le dire.** Décision de la Direction : une demande Ad & Pro de KAM passe par le National Sales puis est TRANCHÉE par Direction Marketing (ex-« chef de produit ») ; celle de tout autre demandeur — le National Sales compris — passe par Direction Marketing puis la Direction. Le bloc générique disparaît ; les pièces liées montrent chacune SES documents, ouvrables, renommables et supprimables en un clic depuis la demande — rendus À L'INTÉRIEUR de la ligne, jamais dans un second bloc « tous les fichiers », qui reproduirait la liste à plat qu'on corrige. **Ce qui ne disparaît PAS avec lui** : la pièce de la demande ELLE-MÊME. Sur un sponsoring, c'est la demande du médecin — obligatoire à la création, et le document que tout le circuit lit. La retirer avec le bloc générique l'aurait rendue INVISIBLE sur l'écran même où elle se juge ; elle garde un emplacement NOMMÉ, appelée par son nom au lieu d'un dépôt où l'on range n'importe quoi. **La garde a un cas nommable** : les documents d'une pièce liée appartiennent à SON module, et quelqu'un qui a Ad & Pro sans Legal voit déjà le titre et le montant d'un engagement rattaché — lui ouvrir ses fichiers lui donnerait le contrat. Sans le droit, ils ne sont même pas CHARGÉS. Et les droits des quatre écrans viennent d'UN calcul (`ad-pro/pieces-liees.ts`) : c'est le défaut mesuré de `ad-pro/attachments.ts`, « chacun l'épelait à sa façon, et chaque orthographe oubliait quelqu'un, qui envoyait alors la facture par mail avec un dossier vide ». **Un écran retirait plus qu'il n'ajoutait** : la vue congrès n'avait AUCUN bloc de pièces liées ; y supprimer le dépôt générique sans monter le bloc aurait laissé une prise en charge sans une seule pièce visible — le contraire de ce qu'on répare.

**Et brancher un document Legal EXISTANT demande DEUX droits, pas un.** Le rattachement ne se faisait qu'à la CRÉATION — la bonne façon quand la pièce n'existe pas encore. Mais la convention est souvent enregistrée dans Legal AVANT, et la seule issue offerte était de la RECRÉER : deux lignes pour le même engagement, deux montants dans les totaux, et celle qui porte les pièces jointes n'est pas celle qui porte le lien. Rattacher, c'est joindre un objet à un autre : il faut pouvoir LIRE le document (sans quoi on rattache une pièce qu'on n'a pas le droit de voir, et le bloc la rendrait lisible à tout le monde) ET pouvoir MODIFIER la fiche cible (sans quoi n'importe qui ajoute des engagements à la demande d'un autre) — les deux par `canAccessEntity`, qui répond par ENREGISTREMENT et non par module (§118.71). **On ne VOLE pas un rattachement** : un document déjà lié ailleurs n'est pas déplacé en silence, le refus NOMME la fiche qui le porte — et le geste qu'il nomme EXISTE, parce qu'un refus qui renvoie vers une action absente est une impasse déguisée en explication (§118.63).

110. **L'audit a attrapé mon propre raccourci, et le test qui l'a rapporté mesurait la moitié de la règle.** J'ai appliqué la migration avec `psql` : elle était donc sur disque et absente de `_prisma_migrations`. Le Test Center l'a vu et rapporté HIGH bloquant — le constat était JUSTE, le remède est `db:deploy`. Mais le test du runner affirmait `status === (criticalCount > 0 ? "FAILED" : "PASSED")` alors que le runner conclut sur `criticalCount > 0 || blockingFailures > 0` : zéro critique, un bloquant, et un test rouge qui accusait le produit au lieu de nommer la vraie cause. **Une assertion qui lit la moitié d'une règle ne mesure pas cette règle** — c'est §118.92 (« qu'est-ce que le juge a réellement mesuré ? ») appliqué à un verdict, et l'échec DIT maintenant lequel des deux compteurs a parlé. Leçon de méthode qui vaut au-delà : appliquer une migration à la main la rend invisible au mécanisme qui vérifie qu'elle a été appliquée ; le chemin documenté existe pour cette raison exacte.

Mon assertion d'ambiguïté était vraie sans être une assertion de ce que je croyais tester, parce que l'ambiguïté a **DEUX branches** que rien ne distinguait dans le banc : deux fiches d'une MÊME nature arrivent dans `candidats` de `resoudreCible` (`retenu` vide, refus par cette voie), tandis que deux natures qui rendent chacune UNE certitude arrivent dans `retenu` — et c'est le CUMUL qui est ambigu. Seule la seconde branche portait le collapse, et aucun cas ne l'exerçait. Un décor où un sponsoring et un événement portent « Soirée Béjaïa » la couvre, le sabotage rejoué tombe. C'est §118.17 dans sa forme la plus fourbe : l'assertion n'était pas tautologique, elle visait simplement **l'autre moitié du mécanisme** — et le seul moyen de le savoir était de casser le code exprès. Corollaire de méthode : un sabotage qui passe ne dit pas « le code est bon », il dit « je ne teste pas ce que je crois ».

113. **Une définition de circuit SANS AUCUNE ÉTAPE était rendue comme un circuit configuré.** Trouvé en lisant la base pour une AUTRE raison — j'enquêtais sur deux tests rouges qui passaient en isolation — et c'est le fait le plus utile de la session : `getDefinition` s'écrivait `if (existing) return existing`, une garde qui regarde la présence de la LIGNE `WorkflowDefinition` et jamais le nombre de ses `WorkflowStep`. 115. **J'ai fait échouer un build propre en lançant deux travaux qui touchent le même fichier — troisième fois de la session que la cause est mon ordonnancement.** Le build a rendu `Module not found: Can't resolve './aiguillage.genere'`, chaîne `executer.ts` → `capacites` → `impl-capabilite` → `assistant.ts` → la route de flux. Le diagnostic RESSEMBLAIT trait pour trait à la régression que ce dépôt a déjà payée deux fois — un module serveur tiré dans un composant client, l'erreur que le typecheck ne voit pas. Il n'en était rien : `graphify:refresh` ÉCARTE `actions/aiguillage.genere.ts` le temps de son scan (§118.76, et son `trap` le restaure), et j'avais lancé le `rm -rf .next && npm run build` EN PARALLÈLE. Le code était juste ; les deux travaux se disputaient un fichier. C'est la même faute que le sous-ensemble de tests lancé contre une base qu'une autre suite mutait (§118.113) : **deux travaux qui touchent la même ressource ne se mesurent pas l'un à côté de l'autre.** La garde ne peut pas être un commentaire — le script en portait déjà un excellent sur le POURQUOI de la mise à l'écart, et il ne disait rien de ce qu'elle CASSE pendant sa fenêtre. Elle s'arme donc sur un fait du processus (§118.17) : si un `next build` tourne, le rafraîchissement REFUSE de commencer, et son refus nomme l'échec qu'il évite. Exercée contre la condition réelle, pas simulée. **L'asymétrie est assumée et elle est la moitié de la règle** : l'inverse — un build lancé pendant le scan — n'est pas couvert, parce qu'il échoue BRUYAMMENT sur un module introuvable. Le coût est un build perdu, jamais un faux succès, et une garde qui laisserait passer en silence serait la seule vraie faute. Corollaire de méthode, jumeau de §118.84 : quand un environnement rend une erreur qui ressemble à un défaut connu, vérifier d'abord **ce qui tournait en même temps** — un `Module not found` prouve qu'un fichier manquait à cet instant, jamais qu'un import est fautif.
